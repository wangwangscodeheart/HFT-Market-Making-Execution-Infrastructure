# 待审：输入准入与 coreSeq 的边界

初始评审记录：第七小轮发现顺序偏差时的分析保留如下。后续已在第八小轮实现准入分类与编号分离，见 ADMISSION_ROUND08.md。本页不修改 ADR 或 V1.1。

## 契约与现状

V1.1 §6.2（04_ARCHITECTURE_BASELINE.md 中“收到业务输入后”段）要求先验证来源、身份及事件完整性，再分配 coreSeq。

当前 CoreLoop::step 在调用 apply 之前取得 command ID、递增 sequence_ 并推进 last_time_；来源、身份与载荷检查分散在 apply 的各分支。因此非法来源的成交或订单证据也会消耗 coreSeq。StepHarness 会把原始输入、结果及状态摘要保留在 trace 中；有些拒绝会造成隔离与停报，而非无状态丢弃。

这是实施与原文顺序的差异，不应将当前序号直接宣传为“全部经过准入的业务事实序号”。目前仅为内存业务诊断，没有 Journal 或发送许可依赖这些序号。

## 为什么本轮不简单调整一行代码

若在入口直接返回且不保留故障事实，会丢失非法证据造成的风险信息；若直接移动递增代码，则必须区分无业务变化的拒绝、必须隔离的外部证据和导致停报的内部故障。不能为了序号看似连续而删除诊断记录，也不能把非法回报作为可信业务证据。

## 建议的最小细化方案（待审）

1. 先做不改变账本的来源/身份/完整性准入判定。
2. 合格业务输入进入核心业务序列；必须保留的非法外部证据，转换为显式、本地生成的拒绝/隔离事实，再按明确契约排序。
3. 原始投递编号与业务 coreSeq 分离，拒绝记录关联原输入；不伪造交易所或柜台序号。
4. 明确本地意图被风控拒绝、重复成交、内存失败和时间回退各自是否取得序号，建立对应测试后实施。

这涉及事件信封和本地拒绝事实的类型约定，应独立审查，不在单个通道枚举修复中悄然改变。不得据此开始 Journal、线程或网关实现。
