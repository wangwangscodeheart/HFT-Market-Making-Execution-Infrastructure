# 第二十七轮：批量回报保留与核心关联查询检查

日期：2026-11-07。

## 已修正的问题

原运行器逐条处理对端回报，遇到第一条失败立即返回。同批余下的回报没有保留；例如撤单响应成功、撤单终态提交失败，或查询第一条成交失败、第二条尚未调用，均可能失去后续交付入口。

新增有界 LocalEvidenceInbox：整批先入内存队列，容量不足时整批不追加，既有队列保持不变；核心返回 None 或 Duplicate 才移除队首。失败项与未尝试项保留，LocalRetryEvidenceInput 显式重试，市场输入不能绕过待交付队列建立新报价。

LocalReportFailureInput 是明确记录的本地测试输入，可指定若干条报告被核心接受后触发一次核心提交失败。它不影响对端已发生的事实，不回滚真实成交，也不冒充生产故障检测。

## 查询与核心关联

原查询检查只核验对端模型内部一致性。新增 review_local_query_for_core，在投递任何成交前校验配置基线/作用域、所有对端订单都能关联核心订单、意图/策略/客户端身份一致、没有遗漏核心已知订单，以及没有遗漏或修改已经记账的成交。

陌生订单返回 UnknownOrder；身份/意图冲突返回 EvidenceConflict；漏掉已知订单或已记账成交保持 Incomplete。检查只读，不把外部持仓覆盖核心账本。查询通过结构检查不等于通过核心关联检查，更不等于恢复证书。

查询失败后 query_blocked 保持，只有再次收到通过检查且交付完成的完整查询才解除这一局部限制。批量重试成功本身不清除查询限制。核心 kill、冲突、风险亏缺等仍独立生效。

## 收件箱溢出

队列容量为对端最大成交行数加两倍核心订单容量。追加失败保留原队列，记录 delivery_loss 并禁止新增报价。排空队列或随后某次完整查询成功都不能清除该丢失标记；当前没有实现解除流程。不能用“队列空了”假设证据没有缺失。

每帧新增 pending_delivery、query_blocked、delivery_loss；导出与页面原始数据可查看这些值。当前页面三个既有案例仍是正常成功轨迹，不把它们当作本轮失败注入路径的独立导出证据。

## 实际验证

新增六项测试：陌生/被修改订单；遗漏核心订单/成交；撤单终态失败后的保留与重试；两条查询成交首条失败时两条都保留；溢出标记不能由排空或查询成功清除；整批容量拒绝不覆盖已收证据。

MSVC Debug / Release 各 **203 项测试、26707 次断言**通过，零失败/跳过。四方测试清单一致，八项证据负控和三组页面 Node 逻辑检查通过；八份既有导出诊断逐字一致。页面数据重新生成为本轮 Release。

证据目录：`evidence-local/2026-11-07-evidence-inbox-debug`、`evidence-local/2026-11-07-evidence-inbox-release`。

## 边界

收件箱仅在内存中，进程退出会丢失，不是耐久日志或生产传输通道。单条核心提交有事务保证，多条回报整体没有回滚；已经成功记账的成交保留，未成功项按记录等待重试。内存分配等异常仍向外传播并锁住运行器，不宣称跨组件异常回滚或自动恢复。
